### 1.2 关键断链事实（全部规划的出发点）

1. **主链路不含诊断与优化**：`pipeline.py:26-27` 只 import 了 `compiler` 两个模块——`run_checkup`
   到"指标聚合 + 确定性校验"为止。FR4/FR5 的诊断、优化、验证、报告能力只能通过
   `scripts/e2e_check.py` 触达（其 import 清单第 23-28 行显式引入 `rules.analyze` / `verify` /
   `render_comparison_report`），网页界面无入口。
2. **R4 规则在任何链路中空转**：`rules.py:13,400-401` 声明依赖 `metrics["o2_compare"]`
   （"由 pipeline 用同码 -O2 实测后填入，本模块不编译"），但全仓 grep 显示没有任何代码产出该字段。
3. **LLM 候选没有落地路径**：`llm_agent.py:80,89,172-175` 的 Schema 已要求输出"完整可编译的
   单文件 C 源码"（`modified_source`），但没有链路把它喂给 `verifier.verify`——验证闭环目前只吃
   `benchmarks/variants/` 里 2 个手写候选（b02、b09）。
4. **设计内延后项**：FR7（编译参数推荐）/ FR8（批量跑分）/ FR9（热点函数排名）为
   `docs/02 §3` 延后需求；FR9 备注"trace 解析已具备数据，差符号关联"。

### 1.3 已知短板摘要

主链路与脚本链割裂（1）；R4 依赖字段无人产出（2）；验证候选仅 2 个手写版本（3）；基准全为
自建微型程序（10^5~10^6 指令量级，无标准基准坐标）；能耗模型为 42 行线性权重；单文件编译单元；
工程侧 `requirements.txt` 未锁版本、无 LICENSE（`docs/08` 已标注待定）。

## 2. 扩展方向清单

### 主线一：可信 AI 优化闭环的纵深

#### D1 · LLM 候选接入验证闭环（"建议→验证"最后一段路）——M

- **解决**：AI 只出建议不出结果，闭环"生成端"靠手写候选。
- **衔接点**：`optimizer/llm_agent.py` 的 `modified_source` 输出 → `optimizer/verifier.py` 的
  `verify` / `verify_many`（数据结构已兼容，缺落盘为候选任务目录的胶水层）。
- **路径**：新增 bridge 层将建议落盘为 `workdir/<task>/candidates/llm-01/`，复用 verify 全流程；
  ACCEPT 候选进入 `verify_many` 最优比较。
- **风险**：T5（LLM 代码不可靠，`docs/08` 列为高概率）——但失败路径全部有状态机兜底，这正是
  闭环卖点；temperature 0.2 已设；无新依赖。

#### D2 · 失败自修复回路（REJECTED → 回喂 LLM → 下一候选）——M（依赖 D1）

- **解决**：一次 REJECT 即终结；把失败原因（build.log 片段 / stdout diff / 指令数反升）回喂
  LLM 生成修订候选，形成"分析→生成→验证→修复"完整循环。
- **衔接点**：`verifier.py` REJECTED 分支产物（verdict.json 含失败原因）→ `llm_agent.py` 上下文注入。
- **路径**：在 D1 的 bridge 层加循环控制器（建议上限 3 轮），每轮将上一轮 verdict 失败原因拼进 prompt。
- **风险**：API 成本与时长（每轮 = 1 次 LLM + 1 次编译 + 2 次 QEMU）；需硬性轮数上限防死循环；
  无新依赖。**全项目研究味最浓、答辩最出效果的方向。**

#### D3 · 规则库扩容（R10+，即插即用）——每条 S

- **解决**：覆盖面扩展：循环展开机会、`memcpy/memset` 系内建替换、除法转移位、fence/CSR 冗余访问等。
- **衔接点**：`optimizer/rules.py` 的 `_RULES` 元组（注册即生效）；证据基建（disasm + trace）全复用。
- **路径**：每条新规则 = 一个 `_rN_*` 函数 + 防误报过滤（仿 R1 的 libc 内部调用过滤先例）+
  `tests/test_rules.py` 固定样例。
- **风险**：误报损伤可信度——沿用"证据不足不输出"纪律；无新依赖。

#### D4 · 多目标验证策略（指令数 / 能耗分可配置）——S（一次性）

- **解决**：`verify_many` 固定取动态指令总数最小者；嵌入式场景可能优先能耗分。
- **衔接点**：`verifier.py` 候选比较逻辑 + `config.toml`。
- **风险**：接近无；配置项做完即止。

### 主线二：可复现 RISC-V 评测平台的横向扩张

#### D5 · 主链路补课（FR4/FR5 接进 pipeline 与 UI）——M

- **解决**：最大的既定设计缺口——诊断/优化/验证/报告能力只在独立脚本里，UI 与答辩演示
  割裂；同时修复 R4 空转（pipeline 中产出 `o2_compare`）。
- **衔接点**：`pipeline.py` 的 `run_checkup` 步骤序列（`app.py:42-53` 的 STEP_LABELS 已预留
  "optimize/verify/report" 标签，接线即用）；`app.py:444` 结果页签扩展；`reports/report.py` 直接复用。
- **路径**：run_checkup 增加可选 `verify=True` 分支：rules.analyze →（有 key 则 llm_agent）→
  verify → report；UI 加"优化建议""验证闭环""对比报告"三个页签。
- **风险**：体检时长从 10~30s 涨到 1~3 分钟（每候选 +1 编译 +2 运行），需分步按钮或显式进度
  提示（NFR4 的 60s 约束仅限体检，需在文档注明）；无新依赖。

#### D6 · FR9 热点函数排名（运行时函数级画像）——M

- **解决**：只有全局类别分布 + 静态每函数行；无法回答"指令都花在哪个函数"。
- **衔接点**：`profiler/trace_parser.py`（已有 PC 全集与 exec 记录）+ `compiler/disassemble.py`
  （objdump 符号表）做 PC→函数区间映射；结果进 `metrics.py` 的 `functions` 字段并反哺规则引擎上下文。
- **路径**：静态符号表建 PC 区间字典 → trace 聚合阶段按区间累加 → 每函数动态指令占比 Top N。
- **风险**：内联函数归属模糊、stripped ELF 无符号（基准未 strip，可暂不处理）；受 FR3 的
  10^6 指令量级约束保护，trace 体积可控；无新依赖。

#### D7 · FR7 编译参数推荐（R4 的泛化）——M

- **解决**：R4 只回答"你比 -O2 差多少"；用户故事 US3 要的是全参数矩阵对比与推荐。
- **衔接点**：复用 `run_checkup` 编排 + `scripts/m1_matrix.py`（已有 30 组合矩阵成熟脚本）+
  `_gcc_version_cache` 式缓存先例（`compiler/config.py`）。
- **路径**：限制矩阵 3 架构 × {O0, O2, Os}（9 组合），异步并发跑，输出"指令数最少组合"推荐卡。
- **风险**：矩阵耗时（9 × ≤60s，最坏 9 分钟——必须并发或裁剪）；multilib 组合残缺
  （`docs/08` T4，需 `-print-multi-lib` 预检）；无新依赖。

#### D8 · FR8 批量跑分 + 历史趋势看板——S

- **解决**：`scripts/m4_scan.py` 已能扫全部基准但只是一次性脚本；缺历史维度。
- **衔接点**：m4_scan 逻辑产品化 → 结果追加 `reports/data/history.jsonl` → `app.py` 加趋势页
  （pandas 已有）。
- **风险**：workdir 产物体积膨胀（2026-09 曾清理 1.6GB——需配"保留最近 N 次任务"策略）；无新依赖。

#### D9 · 标准基准接入（CoreMark / Dhrystone / MiBench 子集）——L

- **解决**：10 个自建微型基准说服力有限，缺乏与外部世界对话的坐标。
- **衔接点**：`benchmarks/` 目录规范（源码 + expected + snapshots 三件套）+
  `scripts/freeze_benchmarks.py` 冻结流程 + golden 机制直接复用。
- **路径**：先接 Dhrystone / MiBench 单文件子集（License 宽松），CoreMark 需处理 EEMBC 许可
  与 bare-metal 移植层（stdout 钩子对接 semihosting）。
- **风险**：**全清单唯一可能触碰诚实红线的方向**——标准基准指令量在 10^7~10^8 级，逐条执行
  trace 将达 GB 级且极慢（`docs/08` T2/T6：Windows 无 TCG 插件）；若用采样/外推会破坏
  "确定性精确计数"红线。**前置依赖**：先设计"大基准下的确定性计数策略"（如仅对热点函数区间开
  trace），红线未解前不启动；另需处理 EEMBC 许可条款。

### 工程与体验增强（一次性）

#### D10 · 能耗模型 v2 ——S

## 4. 长期主线判断

**主线一（纵深）："可信 AI 优化闭环"的自动化程度持续提升**——
D5 → D1 → D2 → D3。演进轴是"候选从哪来"：手写候选（现状）→ LLM 单轮候选（D1）→ 失败自修复
多轮候选（D2）→ 更丰富的规则取证支撑生成（D3）。每推进一步，"AI 验证代码"的差异化
（`docs/01 §6` 创新点一）加深一层，且全部建立在已验证的状态机与证据链之上，不引入新的信任假设。
**可持续迭代的主线。**

**主线二（横向）："从演示工具到可复现评测平台"**——
D6 → D8 → D7 → D9 → D11。演进轴是"能评什么"：10 个微型自建基准 → 函数级画像 → 批量回归与
历史趋势 → 标准基准坐标 → 教学批量服务。兑现 `docs/02` 用户故事 US3/US5（开发者参数选型、
教师课堂演示）的完整承诺，把项目从"参赛作品"变成"有人真的会用的平台"。**第二可持续主线**，
其中 D9 因红线前置依赖放最后。

**明确不做**（与既有边界一致）：真实功耗测量、缓存时序/周期仿真、多线程与内核分析、
多文件构建系统、二进制改写优化。

**相关工程债提醒**（非功能，但在 D11 对外服务与 D9 引入外部代码之前必须先解决）：
`requirements.txt` 未锁版本；无 LICENSE（`docs/08` 材料风险行标注待定，建议 MIT/Apache-2.0）。
