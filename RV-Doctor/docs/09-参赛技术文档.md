## 1. 项目简介

RV-Doctor 原本是一套**面向 RISC-V 的代码性能诊断流水线**：输入 C 源码，自动交叉编译、在 QEMU 裸机运行、解析指令 trace 得到动态指令统计，再由规则引擎与大模型给出优化建议，并用「编译 → 输出一致 → 实测下降」三关验证，失败自动回滚。

本次参赛把它**搬到了 K1 真机上**，变成一台能听懂人话的诊断终端：对着耳麦说「开始体检」，终端在板内完成录音、语音识别、意图判定，执行固定的矩阵乘法体检任务，并把实测结果直接显示在触屏上。全程离线，不上传音频与源码。

两条线的分工：

- **端侧（主线）**：录音 → 前处理 → SenseVoice ASR → 本地千问意图 → 受限任务派发 → 结果呈现；
- **主机侧（子系统）**：同一套「测量归测量、AI 归 AI」的方法论在 QEMU 指令级统计上的实现，提供 10 个基准与验证闭环。

## 4. 关键技术实现

### 4.1 端侧语音链路

- **采集**：`arecord -D hw:CARD=sndes8326,DEV=0`，48 kHz PCM16 双声道。设备用稳定名而非声卡编号——重启后编号会从 1 变 0。
- **前处理**：保留原始录音，做有抗混叠滤波的整倍数降采样到 16 kHz 单声道；统一两级 110 Hz 高通、12 dB 增益与峰值限制；增益、裁剪、哈希全部落盘。
- **识别**：官方 `spacemit_asr` 1.0.2（cp312/linux_riscv64，SHA256 固定）加载 SenseVoice 三件套，显式选择 CPU、4 线程、中文。
- **意图**：本地 `llama-server` 跑 Qwen3.5-2B Q4_K_M，`--parallel 1 -t 4 -c 2048 -ub 32 --reasoning off`，只返回受限 JSON。

### 4.2 受限意图与安全边界

模型不被允许自由行动：输出必须是白名单内的意图（`start_checkup` / `explain_report` / `compare_configs` / `query_system`），解析失败或得到 `unknown` 时**不派发任何任务**，页面提示用户重说。20 条端到端样本中越界派发为 0。

### 4.3 主机侧：QEMU 裸机 + 逐条 trace 精确计数

QEMU 的 linux-user 模式无 Windows 原生版本，因此走 `qemu-system-riscv64/32 + -bios none` 裸机 + 自研最小运行时（`rvcrt0.S` + `link.ld`）。开启 `-accel tcg,one-insn-per-tb=on` 后每个 TB 只含一条指令，`-d in_asm,exec,nochain` 日志中每条 TB 执行记录即对应一条真实执行的指令。

实测锁定并适配了三个会直接导致数字错误的格式坑（均有固定样例日志测试防回归）：

1. **exec 行 PC 字段自适应定位**：不硬编码版本偏移，用 `IN:` 段 PC 全集交叉验证定位，兼容 QEMU 8.x/9.x/11.x；
2. **符号注解行**：QEMU 11 会在行尾附加符号名，解析不当曾漏计 84% 的指令；
3. **引导 ROM 剔除**：只统计 DRAM 区（PC ≥ 0x80000000），复位向量首条偶发重复执行的干扰剔除，剔除量进诊断字段。

确定性红线：同一 ELF 两次运行的动态指令数与类别分布完全相等，因此主指标取动态指令数而非墙钟时间。

### 4.4 验证闭环状态机

```
PROPOSED → 编译 → COMPILED → 输出比对 → TESTED → 确定性校验 → MEASURED → 指标对比 → ACCEPTED
    └──────── 任一步失败 ────────→ REJECTED（自动回滚原版，保留失败证据）
```

ACCEPT 条件：编译成功 **且** stdout 与 golden 一致 **且**（动态指令数下降 **或** 能耗分下降）。原版源码永不覆盖。

### 4.5 单变量调优方法与证据

阶段 4 只改一个变量：千问的物理批大小 `-ub 128 → 32`。其余配置（线程、上下文、并发、模型、提示词）与输入顺序完全相同，20 条音频逐条对比 JSON 合法性、意图、实际派发，结果 20 条逐条一致、无回归。整体千问 API 响应中位由 34.10 s 降到 12.66 s，首内容中位由 31.23 s 降到 9.77 s。

控制探针（同一序列三条不同转写）显示：第 1 条没有前缀可复用，两臂都约 34 s；第 2、3 条的响应中位数由 34.81 s 降到 13.25 s，差距来自提示词复用——基线第 2、3 条命中缓存 **0 / 2** 个 token，候选为 **90 / 90** 个。（`122` 这个数字属于另一组「同一句连续重复」测量，不是本对照的基线缓存。）

**同时暴露的代价**：同一句连续提交的第二次响应由 4.71 s 增至 12.26 s（较小批大小让可复用状态变少）。因此该配置按「多条不同语音请求」场景接受，不宣称对所有请求都更快。

## 5. 实测结果

**板端环境**：K1 MUSE Pi Pro，Bianbu LXQt，Python 3.12.3，`gcc`（RISC-V），`llama-server`（spacemit 分支），SenseVoice 量化 ONNX。

### 5.1 阶段 1：本地 ASR 与 CER（三组口径并列）

| 轮次 / 配置 | 结果 | 说明 |
|---|---|---|
| `round-19e7f20b8f73`（首轮） | 81/76 = **106.58%** | 每句均有整句或近似整句重复，判定为采集方式问题 |
| `round-6e90e6b91134`（现场单遍） | 22/76 = **28.95%** | 5 条完全正确，ASR-04 仅返回标点；**未达 20% 门槛** |
| `replay-vad-off`（关闭自动裁切） | 17/76 = 22.37% | 证明重复主要来自 VAD 裁切 |
| `replay-filter`（统一前处理） | 14/76 = **18.42%** | **通过门槛**；10 条识别 3.57–3.67 s/条 |

评分规则：NFKC、英文小写、移除 Unicode 空白与标点，按字符 Levenshtein 距离汇总。现场成绩与复跑成绩分别记账，不以复跑替代现场。

### 5.2 阶段 2：端到端验收（20 条）

| 模式 | JSON 合法 | 意图正确 | 越界派发 | 任务失败 | 时延 |
|---|---:|---:|---:|---:|---|
| `text_intent`（20 条参考文本） | 20/20 | **20/20** | 0 | 0 | API 中位 35.08 s |
| `audio_e2e`（20 条真实音频） | 20/20 | **18/20** | 0 | 0 | 文件→结果中位 39.01 s |

两处误判：解释报告类回退 `unknown`；系统查询误触发固定体检。两者都不会造成越界动作。

### 5.3 阶段 3：同一录音重复测量（3 次）

同一固定 WAV（SHA256 校验）经页面连续回放三次：

| 轮次 | 停止→结果 | 千问预填充 | 说明 |
|---|---:|---:|---|
| 1 | **39.239 s** | 30.028 s | 模型已加载但提示词缓存近乎未命中（仅命中 1 个 token） |
| 2 | **10.318 s** | ≈1.17 s | 复用 122 个提示词 token |
| 3 | **10.306 s** | ≈1.17 s | 同上 |

三份体检结果均与参考一致。资源：ASR 调用 3.59–3.65 s，任务派发约 0.51 s；回放与千问服务 cgroup 合计峰值 2522.36 MiB，整机可用内存最低 13163.49 MiB。**4 s 目标未达到**，冷热态差距主要来自预填充。

### 5.4 阶段 4：配置调优（单变量）

| 指标 | `-ub 128` | `-ub 32` | 变化 |
|---|---:|---:|---|
| 千问 API 响应中位数 | 34.10 s | **12.66 s** | **−62.86%** |
| 文件→结果中位数 | 39.01 s | **18.00 s** | −53.9% |
| 20 条 JSON / 意图 / 派发 | 20/20 · 18/20 · 一致 | 同上 | 不降 |
| 同一句第二次响应 | 4.71 s | 12.26 s | 变慢（已披露） |

### 5.5 K1 上 OpenMP 夹具（b02）

`gcc -std=c11 -O2 -fopenmp` 编译固定 `b02_matrix_mul.c`，四线程与八线程各跑 3 次，stdout 均与 golden 一致（`checksum=10584629`），中位墙钟 5.14 ms / 5.57 ms，构建 0.77 s。该夹具只用于证明「K1 上能编译并正确并行执行 RISC-V 代码」，不与 QEMU 指令数混比。

### 5.6 主机侧基准集（rv64gc / O0，动态指令数确定性可复算）

| 基准 | 算法核心 | 动态指令 | 调用次数 |
|---|---|---:|---:|
| b01_sum_array | 数组累加 | 95,021 | 164 |
| b02_matrix_mul | 16×16 矩阵乘 | 163,456 | 176 |
| b03_crc32 | 逐位 CRC-32 | 24,353 | 160 |
| b04_string_search | 朴素匹配 | 137,475 | 1,848 |
| b05_bubble_sort | 冒泡排序 | 278,255 | 200 |
| b06_grayscale | 浮点灰度 | 28,369 | 164 |
| b07_fib | 递归斐波那契 | 162,583 | 5,337 |
| b08_dot_product | 点积 | 167,089 | 168 |
| b09_strlen_loop | 循环内 strlen | 46,318 | 346 |
| b10_window_sum | 滑动窗口 | 320,853 | 202 |

两个能说明「RISC-V 指令特征」的对照：

- **b06 跨架构退化**：RV64GC 28,369 条 → RV64I 352,363 条（12.4 倍），函数调用 164 → 4,537（27.7 倍），原因是无 F/D 扩展时浮点退化为 `__mulsf3` 等软浮点例程；
- **b09 编译等级边界**：-O0 46,318 → -O2 9,075（−80.4%），但调用只降 43.1%，说明编译器之外仍有源码级优化空间。

### 5.7 质量保证

- 主机侧 **166 个 pytest 用例**分层：单元（不依赖工具链）→ 集成（真实 GCC/QEMU，缺失自动跳过）→ 回归（10 基准 golden + 快照零浮动）；
- 端侧验收脚本 `validate.py` 支持 `text_intent` / `audio_e2e` 两种模式，逐条落盘；
- 每个数字都有对应 JSON；部署清单带 SHA256，板端复算哈希一致。

## 6. 边界与诚实声明

| 声明 | 说明 |
|---|---|
| 时延未达标 | 4 s 目标没有达到，热态 10.3 s、调优后 18.0 s 均照实写 |
| CER 分口径 | 现场 28.95% 未通过；18.42% 是同源换前处理后的复跑结果，两者不合并 |
| 样本局限 | 10 条录音来自同一人、同一耳麦、同一房间，结论不外推到其他说话人与噪声环境 |
| AI 核占用未测 | 不声称满足「AI 核 ≥90%」的硬件利用率评分项 |
| 能耗是估算 | 主机侧能耗分 = Σ(指令类别计数 × 可配置权重)，仅用于前后对比 |
| QEMU 不模拟缓存 | 缓存友好性只作静态提示，不作为实测指标 |
| 等价性有限 | 输出一致性校验针对当前测试输入，不构成对所有输入的等价性证明 |
| 个人语音不入库 | 仓库只保留信号统计与评分 JSON，录音文件不公开 |

## 7. 复现指南

**板端（主线）**

1. 按 `板端验证/asr/README.md` 准备 venv、`spacemit_asr` 1.0.2 wheel 与 SenseVoice 模型（用 `download_resources.py` + `manifest.json` 核对哈希）；
2. 按 `RV-Doctor/edge_terminal/README.md` 部署终端文件与依赖，启动 `llama-server`；
3. `python3 tasks.py --seed` 准备固定报告与对照数据，再启动 `terminal.py --port 18793`；
4. 电脑侧 `adb forward tcp:18793 tcp:18793`，浏览器打开 `http://127.0.0.1:18793/`；
5. 复跑验收：`validate.py --mode text_intent` / `--mode audio_e2e`，报告写入 `validation/<run_id>/report.json`。

**主机侧（子系统）**

1. Python 3.11+ 建 venv 并 `pip install -r requirements.txt`；
2. 按 `docs/04-环境搭建指南.md` 安装 xPack GCC 与 QEMU（可便携安装到 `tools/`）；
3. `scripts\run_all_checks.bat` 全量复算；
4. `.venv\Scripts\python.exe -m streamlit run app.py --server.port 8501`。

## 8. 开发过程

单人 + AI 辅助开发。主机侧按 M0–M7 里程碑推进（`docs/05-开发路线图.md`）；K1 改造按阶段 0–5 推进，检查表与逐条记录见 `docs/edge/执行计划.md`。工程纪律：外部命令一律 subprocess 参数列表调用；统计必须来自真实解析；未达标的数字不改口径；每次实验保留命令、参数、哈希与失败原因。

**AI 使用的边界**：AI 用于代码草拟、文档整理与结果核对，不参与「结论」——所有性能与准确率数字由脚本从落盘证据算出，AI 只做转述。
