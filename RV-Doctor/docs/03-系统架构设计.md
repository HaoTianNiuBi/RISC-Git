# 03 系统架构设计

> 本文档给出模块划分、接口定义、数据模型与关键技术选型论证。需求见 [02-需求说明](02-需求说明.md)，环境见 [04-环境搭建指南](04-环境搭建指南.md)。

---

## 1. 设计原则

1. **数据实测**：任何指标必须来自工具链真实输出；解析器只做"翻译"，不做"估计"。
2. **模块解耦**：UI 层不直接调用工具链，一律经由 pipeline；每个模块可独立 pytest。
3. **可降级**：LLM 不可用 → 仅规则引擎；trace 不可用 → 仅静态分析；每级降级在界面明确标注。
4. **证据留存**：每次任务的全部产物（日志、stdout、trace、JSON）按任务目录归档，报告中的数字必须可复核。

## 3. 端到端数据流

| 步 | 动作 | 输入 | 输出（落盘 workdir/<task_id>/） |
|---|---|---|---|
| 1 | 接收源码 | 粘贴文本 / 上传文件 | `src/`（源码或 ELF） |
| 2 | 编译 | 源文件 + 架构 + 优化等级 | `app.elf`、`build.log` |
| 3 | 反汇编 | `app.elf` | `disasm.txt` + 静态统计 |
| 4 | 运行 | `app.elf`（QEMU + semihosting + trace） | `stdout.txt`、`trace.log` |
| 5 | 解析 trace | `trace.log` | `trace_stats.json`（PC→助记符、执行计数） |
| 6 | 聚合指标 | 静态统计 + trace 统计 | `metrics.json` |
| 7 | 规则分析 | 源码 + `disasm.txt` + `metrics.json` | `findings.json` |
| 8 | LLM 建议 | 源码摘录 + 指标 + 发现 | `suggestions.json`（可降级） |
| 9 | 验证候选 | 候选源码 | 候选子目录重复步 2~6 + `verdict.json` |
| 10 | 报告 | 上述全部 | `report.md`（前后对比表 + 数据来源注脚） |

## 5. 模块与关键接口（函数签名级）

### 5.1 compiler/riscv_compile.py

```python
@dataclass
class CompileResult:
    ok: bool
    elf: Path | None
    returncode: int
    log_path: Path          # build.log 全文留存
    stderr_tail: str        # 错误摘要（前端展示用）

def compile_source(
    src: Path,
    arch: str,              # "rv32i" | "rv64i" | "rv64gc"
    opt: str,               # "O0" | "O1" | "O2" | "O3" | "Os"
    workdir: Path,
    timeout: float = 60.0,
) -> CompileResult:
    """构造 [gcc, -march, -mabi, -Ox, --specs=rdimon.specs, 链接参数, ...]
    参数列表，subprocess.run(capture)，日志落盘。禁止 shell=True。"""
```

编译参数由 `arch` 映射表统一管理（march/mabi/emulator 位宽），链接统一追加 semihosting 支持与 `virt` 机器的 DRAM 首地址（`0x80000000`，详见 04 文档 FAQ）。

### 5.3 profiler/runner.py

```python
@dataclass
class RunResult:
    ok: bool                 # 退出码 0 且 stdout 非空
    stdout: str
    exit_code: int | None
    timed_out: bool

def run_baremetal(
    elf: Path,
    workdir: Path,
```

### 5.4 profiler/trace_parser.py

```python
@dataclass
class TraceStats:
    pc_mnemonic: dict[int, str]   # 来自 in_asm 段：PC → 助记符
    exec_counts: dict[int, int]   # 来自 exec 段：PC → 执行次数

def parse_trace(log_path: Path, max_bytes: int = 2**30) -> TraceStats: ...
```

解析器按 QEMU **锁定版本**的日志格式实现，格式细节集中在一个适配函数中，版本升级时只改这一处（08 风险 T1）。确定性保证：统计只依赖日志内容本身。

### 5.7 optimizer/rules.py

```python
def analyze(src: Path, disasm: StaticStats, metrics: dict) -> list[dict]:
    """返回 Finding 列表（schema 见第 6 节）。只读分析，绝不修改源码。"""
```

规则清单（编号固定，便于测试与演示引用）：

| 编号 | 规则 | 主要证据来源 |
|---|---|---|
| R1 | 循环不变量重复计算（如循环内 `strlen`、边界重算） | 源码 AST/正则 + 循环体内 call 计数 |
| R2 | 循环内重复读取不变内存（重复 load 同地址） | 动态 load 计数与地址模式 / 反汇编 |
| R3 | 高频函数调用（递归、微小函数未内联） | jal/jalr 计数 + 函数表 |
| R4 | 编译等级不足 | 同码异级实测对比（-O2 vs 当前） |
| R5 | 冗余类型转换（sext.w/zext 高频模式） | 助记符频率 |
| R6 | 分支密集，可查表/无分支化/提前退出 | branch 占比 + 循环结构 |
| R7 | 重复内存访问（同一表达式多次 load） | 反汇编窗口内相同基址 load |
| R8 | 寄存器溢出（函数内大量 sp 相对 load/store 对） | 函数内 sd/ld(sp) 配对统计 |
| R9 | 浮点软浮点退化（RV64I 下 call `__mulsf3` 等） | 符号名匹配 + call 计数 |

## 8. 关键技术选型论证：为什么是 "qemu-system + semihosting + trace 解析"

**约束**：本项目确定运行在 Windows 原生环境（无 WSL 依赖）。而 QEMU 的 **linux-user 模式不存在 Windows 版本**——`qemu-riscv64`（用户态）只能运行在 Linux 宿主上。这是整个技术路线的分叉点。

| 候选路线 | Windows 可行性 | 动态指令统计 | 结论 |
|---|---|---|---|
| A. qemu-user（用户态模拟） | ❌ Windows 无此模式 | -plugin libinsn 很方便 | 仅作为 WSL2 升级路径（04 文档附录 A） |
| B. qemu-system + 裸机 + semihosting | ✅ 官方 Windows 构建自带 riscv64/32 系统模拟 | ✅ `-one-insn-per-tb -d in_asm,exec,nochain` 日志可精确计数 | **主路线** |
| C. Spike | ⚠️ Windows 构建困难，需自行编译 | `--log` 逐条指令 | 备选，不依赖 |
| D. QEMU TCG plugin（`-plugin`） | ⚠️ Windows 构建对插件支持不可靠 | 插件级精确计数 | 与 A 绑定，留给 WSL2 路线 |

**路线 B 的精确计数原理**：开启逐条执行（QEMU ≥ 10 用 `-accel tcg,one-insn-per-tb=on`，8.1~9.x 用 `-one-insn-per-tb`，更早用 `-singlestep`）后，每个翻译块只含一条指令，`-d exec` 日志中每条 TB 执行记录即对应一条真实执行的指令；`-d in_asm` 提供 PC → 助记符映射；`-d nochain` 防止块链接导致执行日志缺记。两者结合即可得到精确的动态指令总数与类别分布，且结果**确定可复现**（M0 已在 QEMU 11.1.0 上实测日志格式）。

**代价与对策**：逐条执行速度慢（约慢一个数量级）→ 基准程序规模控制（06 文档），动态指令数控制在 ~10^6 量级；trace 日志较大 → `-D` 落盘 + 流式解析 + 大小上限。

**升级路径**：若后期迁移到 WSL2，切换 qemu-user + TCG 插件（libinsn/libctxt等），`runner.py` 与 `trace_parser.py` 的接口保持不变，仅换实现——这是把运行/解析设计为独立模块的原因。

## 9. 可靠性设计

| 风险点 | 机制 |
|---|---|
| 外部命令挂死 | 所有 subprocess 带 `timeout`，超时强杀进程树 |
| 输出爆炸 | stdout/trace 设字节上限，超限标记 `truncated=true` 并在报告中声明 |
| 非法输入源码 | 编译阶段即失败，进入错误分支，不进入运行阶段 |
| 任务互不干扰 | 每次分析使用独立 `workdir/<task_id>`，失败产物也保留 |
| QEMU 版本格式变化 | trace 解析格式适配层 + 固定样例日志测试锁定（08 风险 T1） |
| LLM 返回不可靠 | JSON Schema 校验 + 字段白名单 + 丢弃即记录；闭环兜底（verifier） |
