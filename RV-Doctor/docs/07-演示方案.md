# 07 演示方案

> 面向预赛演示视频与总决赛现场演示。核心原则：**演示中的每个数字都是当场真实运行产生的**，报告模板中的示例值在演示前用实测值替换。

## 1. 演示主线（约 8 分钟）

| 幕 | 内容 | 台词要点 |
|---|---|---|
| 1 开场（30s） | 一句话介绍 + 架构图一页 | "输入 C 代码，输出一份经过验证的 RISC-V 优化报告——每一条结论都有指令级证据" |
| 2 体检（2min） | 上传低效代码 → 点"RISC-V 性能体检" | 展示指令总数、类别分布饼图、热点函数；强调"数字来自 QEMU 逐条指令 trace" |
| 3 诊断（2min） | 规则引擎发现列表 + AI 建议 | 挑一条展开：汇编证据 → 动态计数 → 可信度 87% 这类评分的依据 |
| 4 优化+验证（2.5min） | 点"自动优化" → 状态机逐步走 → ACCEPT | 强调"AI 改的代码要过三关：编译、输出一致、指令数实测下降，不过就回滚" |
| 5 报告（1min） | 前后对比表 + 图表 + 免责声明 | 收尾：性能—能效联合视角；"不替代真实硬件功耗测试" |

## 2. 三个演示场景

### 场景 A：b02 矩阵乘法 —— 循环与访存优化

- 展示目标：R1/R2/R7 规则（重复寻址、重复访存）→ 指针化/循环序调整 → 动态指令下降。
- 讲解点：优化前后反汇编对比（同屏展示内层循环体），指出重复的乘法寻址指令在优化版中消失。

### 场景 B：b09 strlen_loop —— 循环不变量外提（招牌戏）

- 展示目标：最经典的教科书级优化，规则 R1 证据链最清晰（循环体内 `jal strlen` 的动态调用计数）。
- 讲解点：AI 建议的"依据"字段如何把 10,000 次循环 × 每次约 N 条指令换算成预期收益；验证闭环三关全过的状态轨迹展示。
- 备选加强：同时展示 -O0 与 -O2 下同一代码的体检对比，说明"编译器已经做的优化"与"源码级优化"的差别（诚实回应"-O2 就够了"类质疑）。

### 场景 C：b06 grayscale —— 架构适配（RV64I 软浮点高光）

- 展示目标：RV64I 无硬件浮点时，float 运算退化为 libgcc 软浮点调用（`__mulsf3` 等）；AI 建议整数移位近似后指令数骤降。
- 讲解点：这是"面向 RISC-V 指令特征的优化"最直观的证明——同一个算法，架构约束不同，最优写法不同。
- 附加展示：函数调用次数从数万（每次像素 3 次软浮点调用）降到接近 0 的对比。

## 6. 常见提问与回答口径

| 可能的提问 | 回答口径 |
|---|---|
| 能耗分数是真的功耗吗？ | 不是。是基于指令类别权重的相对估算，只用于优化前后趋势对比，界面和报告都带免责声明；真实功耗需硬件测量，超出纯软件项目边界 |
| 为什么用指令数不用运行秒数？ | 动态指令数是确定性的（两次运行完全一致、可复核）；模拟器墙钟受宿主机影响只能作参考值。指令数下降本身就是性能提升的可靠代理指标 |
| -O2 编译器不就优化了吗？ | 演示场景 B 特意对比：-O2 能消除部分问题，但循环不变量、算法级重复（如 b07 递归）源码级优化依然有效，且本平台能告诉你"编译器已经做了什么、还剩什么可做" |
| QEMU 和真机一致吗？ | 指令序列语义一致；时序/缓存行为不同。所以我们的结论限定为"指令数与能耗趋势的相对对比"，不做绝对性能声明 |
| AI 改错了怎么办？ | 这正是验证闭环存在的意义：编译失败、输出不一致、指令数不降三者任一发生都会自动回滚，并保留失败证据——演示中我们专门展示一次失败的回滚 |
| 数据会不会是编的？ | 每个数字可溯源到 workdir 产物；一键自检脚本当场复算全部基准 |
