# 07 演示方案（K1 版）

> 面向预赛演示视频与总决赛现场演示。核心原则不变：**演示中的每个数字都是当场真实运行或可点开的证据文件**。

## 1. 演示主线（约 6 分钟）

| 幕 | 时长 | 内容 | 台词要点 |
|---|---|---|---|
| 1 开场 | 30s | 开发板实物 + 触屏首页 | "这是一台 K1 开发板。它现在能做一件事：听懂你说的话，当场跑一次体检，把结果给你看——全程离线。" |
| 2 语音体检 | 2min | 点开始 → 说「开始体检」→ 识别 → 意图 → 任务执行 → 结果显示 | 强调"录音在板内处理，音频不出板、代码不上云"，并念出实测耗时口径 |
| 3 边界与失败 | 1.5min | 说一句超范围的话（如「帮我订电影票」）→ 显示 `unknown` 且**不派发**；再看一次失败/重说的处理 | "它不会替你猜。认不出意图就停下来问你，而不是乱执行。" |
| 4 证据 | 1.5min | 翻验收报告与执行计划检查表 | 展示 20/20 JSON、18/20 意图、CER 两套口径、调优前后对比 |
| 5 收尾 | 30s | 一句话 + 仓库地址 | "先测量、再让 AI 说话、最后用证据收口。" |

**时间分配提醒**：热态一次完整交互约 10 秒，冷启动约 39 秒。演示前必须**预热一次**，否则观众会盯着 39 秒的等待。

## 2. 三个必演场景

### 场景 A：语音体检闭环（主场景）

- 操作：点「开始」→ 界面提示"现在说话"→ 说「开始体检」→ 点「停止」→ 等待 → 结果页出现校验和 `checksum=10584629`、停止到结果的墙钟耗时与任务回执。
- 讲解点：录音 → 前处理（16 kHz 单声道）→ SenseVoice（约 3.6 s/条）→ 千问意图（热态约 10 s）→ 执行固定 `b02_matrix_mul` 体检 → 结果回显。
- 可点开的证据：`板端验证/edge/results/audio_e2e-c2413d24143c.json`（20 条逐条记录）。

### 场景 B：边界与失败处理（体现"不越界"）

- 操作：说「帮我订一张明天的电影票」→ 界面显示 `unknown` 并提示重说，**没有任何任务被派发**。
- 加固镜头：说一句含糊的「弄一下」→ 同样不派发。
- 讲解点：意图白名单 + JSON Schema 校验；20 条样本中越界派发 0 次。
- 诚实补充：18/20 里有 2 条误判（解释报告回退 `unknown`、系统查询误触发体检），这两条也放出来，说明"误判的方向是保守的"。

### 场景 C：单变量调优前后（体现"性能优化"）

- 操作：打开 `板端验证/edge/results/ubatch-128-vs-32-comparison.json`，展示对照表。
- 讲解点：只改 `-ub 128 → 32`，其余配置与输入顺序完全一致；千问 API 中位 34.10 → **12.66 s（−62.86%）**，文件→结果 39.01 → **18.00 s**，20 条逐条一致、无回归。
- 必须同时说代价：同一句连续第二次由 4.71 s 增至 12.26 s，所以这是"多条不同请求"场景下的选择。

## 4. 演示前 Checklist

**提前 30 分钟：**

- [ ] 板子通电、USB 数据线连接、`adb devices` 能看到设备；
- [ ] `adb forward tcp:18793 tcp:18793` 转发成功，浏览器打开终端页返回 200；
- [ ] 两个服务在跑：ASR 采集（18791）与语音终端（18793）；千问 `llama-server` 在 `127.0.0.1:18080`；
- [ ] **预热一次**：先随便说一句走完一轮，让千问进入热态（否则第一轮 39 秒）；
- [ ] 耳麦插紧（驱动报告 Headset Jack 状态 20），确认录音电平不削波；
- [ ] 关闭系统通知与自动更新弹窗；屏幕亮度调高，避免 800×480 反光；
- [ ] 准备好"超范围指令"的台词（场景 B）；
- [ ] 录像前先空跑一遍完整链路，确认没有卡在"识别中"。

## 5. 兜底降级（按顺序）

1. **千问没起来 / 第一次特别慢** → 先跑一次预热，或直接播预录片段衔接；
2. **麦克风失灵** → 用终端页的文本输入通道演示同样的意图链路，并在解说中说明这是文本通路；
3. **板子整体不可用** → 播放预录完整视频，同时展示证据 JSON；
4. **评委要现场复现** → 用 `validate.py --mode text_intent` 现场跑 20 条，约 10 分钟，不依赖麦克风。

## 6. 常见提问与回答口径

| 提问 | 回答 |
|---|---|
| 现场 CER 28.95% 不是没过 20% 吗？ | 没过。现场单遍朗读受自动静音裁切影响，出现了整句重复；同一批录音关裁切 + 统一前处理后复跑 18.42%。两个数我们都写进文档，不用复跑成绩替换现场成绩。 |
| 4 秒延迟目标达到了吗？ | 没有。热态 10.3 秒，调优后文件到结果 18.0 秒。我们的优化把千问 API 中位从 34.1 秒降到 12.7 秒，但离 4 秒还有距离，文档里写的是"未达"。 |
| 为什么不用 CV？ | 赛题要求 CV/ASR/LLM 至少两种，我们选了 ASR + LLM，把力气花在闭环可靠性上。接摄像头只会多一个演示点，不会提高闭环可信度。 |
| AI 核占用多少？ | 没测。我们的链路主要跑在 CPU 上（ASR 4 线程、千问 4 线程），所以"AI 核 ≥90%"这一项我们不声称。 |
| 模型是本地跑的吗？ | 是。`spacemit_asr` 与 `llama-server` 都只监听板内 `127.0.0.1`，演示时拔掉网线也能跑。 |
| 数据会不会是编的？ | 每个数字对应一个 JSON，路径写在文档里；现场可以用 `validate.py` 重跑一遍。 |
| 断电了怎么办？ | 两个服务可重启；录音只写本地文件，重启后重新开始一轮。断电恢复的压力测试我们没做，风险表里标了"部分开放"。 |
| 和主机侧那套 QEMU 工具什么关系？ | 同一套方法论向下延伸：没有硬件时用 QEMU 做指令级统计。它是子系统，不是本次主线。 |
